# متابعة حماية الإغلاق والقراءات

الحالة: PR مسودة؛ **بروتوكول الإغلاق نموذج أولي منفصل غير مربوط بالتطبيق، ولا يحمي الإغلاق الحالي**. لا تنشر أو تعتمد الجرد حتى اكتمال التنفيذ والاختبارات الفعلية.

## نموذج الإغلاق

أضيف `stocktake-closure-prototype.js` للتحقق من قائمة مجموعات ثابتة وجولة إغلاق وهوية موظف وجهاز مسجل لكل مجموعة، ومنع الإقرار عند وجود مسودات أو عمليات جارية، ومنع العد الجديد بعد الإقرار، ورفض إغلاق عند غياب إقرار أو اختلاف الجولة. `tests/closure-prototype.cjs` يغطي رفض الانقطاع/المعلّقات ومجموعة مفقودة وعزل الفرعين؛ `tests/closure-transaction-race.cjs` يحاكي30 سباقًا بمعاملات متفائلة ومعرّف إيصال ثابت. **هذه اختبارات نموذج محلي، وليست اختبار Firebase أو برهانًا لسلامة التطبيق الحالي.**

لكي يصبح هذا ضمانًا فعليًا يلزم: دمج طلب الإغلاق مع تجميد قائمة المجموعات وتسجيل الأجهزة، قفل الإدخال محليًا قبل فحص كل مفاتيح المسودات وجميع التبويبات، قراءة مستند المجموعة ضمن كل معاملة عد وملاحظة، معاملة إقرار تنافس العد على المستند نفسه، ثم معاملة إغلاق تقرأ الحملة وجميع المجموعات وتتحقق من المجموعة المسجلة والجولة. ينبغي التعامل مع تعذر قراءة التخزين كمانع إقرار، وأن تؤدي إعادة الفتح إلى جولة جديدة. يلزم فرض العملية بقواعد Firestore والمصادقة الخادمية، وإدارة العملاء القدامى والسباقات بين التبويبات وتغييرات المجموعات. الإقرار القادم من جهاز واحد لا يثبت سلامة جهاز مجهول آخر بدون فرض تسجيل الأجهزة. لا يمكن افتراض نشر هذه القواعد أو صحتها.

## تحسين قراءات الإدارة

تم تحويل مستمع `stocktake_audit` إلى تحميل عند فتح تبويب السجل؛ بعد الفتح يبقى لحظيًا حتى تغيير الحملة، ويُلغى عند تبديلها. يوجد مؤشر تحميل وخيار إعادة المحاولة عند الفشل. اختبار `tests/recovery-audit-listener.cjs` ينفذ دوال الصفحة ويفحص عدم الاشتراك قبل فتح التبويب، وعدم تكرار الاشتراك وإلغاءه عند تغيير الحملة. واختبار `tests/recovery-admin-mobile.cjs` يفتح الصفحة فعلًا في Chromium بثلاثة عروض (320 و390 و412 بكسل)، ويختبر تحديث السجل بعد اشتراكه دون اتصالات إنتاج.

التوفير المتوقع عند فتح حملة دون فتح تبويب السجل: حتى300 قراءة مستند أولية وفق حجم نتيجة الاستعلام، إضافة إلى تحديثات الاستعلام خلال فترة الزيارة. هذا استنتاج من مسار الاستعلام، وليس قياس فوترة؛ قد تختلف التكلفة وفق إعادة الاتصال، القواعد والفهارس. إذا فُتح التبويب، فلا يُدعى توفير قراءة التحميل. لا تزال مشكلة `limit(300)` غير المرتب زمنيًا قائمة، وتحتاج فهرسًا مناسبًا وتصفح صفحات دون فقدان السجلات.

## سيناريو 8 أجهزة / 1500 صنف

وفق افتراضات التقرير السابق: 750 صنف لكل فرع، أربعة أجهزة لكل فرع، عملية واحدة لكل صنف، ومدة8 ساعات: 6000 قراءة تحميل أصناف؛ 7500 قراءة معاملات وإيصالات؛ قرابة6000 قراءة تحديثات المستمعين؛ 3000 قراءة تحميل/تحديث أصناف إدارة؛ وقرابة5120 قراءة من مراقب حضور يستمع لمسارين. التقدير قبل تفاصيل التحكم والقواعد والتجارة والنسخ/المحاولات **نحو27,620 قراءة** إذا لم يُفتح سجل التدقيق؛ إذا فُتح يجب إضافة تحميل السجل وتحديثاته، ولا يمكن افتراض1500 قراءة ثابتة له. الكتابات النموذجية نحو8120 (3000 للعد و5120 لمساري الحضور)، قبل سجلات النشاط والعمليات الأخرى. هذه أرقام حسابية افتراضية، وليست قياس Firestore أو ضمان الحصة. إذا عُد الصنف في أكثر من نطاق يزداد عدد العمليات.

لا تزال أرقام الخمول الحقيقية وأسباب الزيادة المسجلة في حساب Firebase غير محسومة. فحص GitHub recovery نجح في a263f4e؛ فحوص أخرى فشلت، وبعضها تاريخي يحتاج تحليلًا. لم تُختبر مصادقة Firebase أو قواعدها أو iOS فعليًا في هذه الجلسة.
